# Independent arithmetic and search validation (C06)

## Oracle provenance and isolation

The test oracle is Bitcoin Core's [libsecp256k1 v0.6.0](https://github.com/bitcoin-core/secp256k1/tree/v0.6.0),
commit `0cdc758a56360bf58a851fe91085a327ec97685a`. The unmodified subset under
`third_party/secp256k1-oracle/` includes upstream `src/`, `include/`, `cmake/`, the
CMake entry point and notices/documentation. Its MIT notice is retained as
[COPYING](../third_party/secp256k1-oracle/COPYING). The source was fetched over
HTTPS from the official repository; no release-signature verification is claimed.
[The lock file](../tests/oracle/secp256k1.lock.json) records SHA-256 for every
imported file and the exact revision. Updating it requires an explicit dependency
change and rerunning the corpus. It is an integrity pin, not an independent
attestation of source authenticity.

Only `BUILD_TESTING=ON` adds the oracle. Upstream CMake builds a static library
with its assembly and optional modules disabled, using its own compiler options.
No keyhunt arithmetic is linked into the oracle probe, and no oracle library is
linked into the production executable. No build-time download, system package or
network connection is needed. Sanitizer builds instrument the oracle as well as
our probes. Upstream's full test suite is not enabled by this integration; the
library's context self-test and the checks below run.

## Independent expectations

`oracle_selftest` checks the source pin, committed public vectors and an independent
Python affine implementation against the pinned library's public API. It covers
128 seeded random valid scalars, carry boundaries above 32/64/128/192 bits,
zero/order/over-wide-domain scalar rejection, SEC1 parsing, point addition,
doubling, opposite points, negation and explicit infinity. Infinity is represented
as `inf` in the test protocol; libsecp256k1 reports an infinity sum as failure to
produce a public key. The harness handles the identity element explicitly because
it has no SEC1 public-key encoding.

The 36 [fixed public vectors](../tests/oracle/vectors.json) are regenerated by the
Python model and checked against libsecp256k1 before being written. The initial
release run passed 1,082 comparisons with seed `0xC06A11CE`; see
[oracle evidence](baselines/C06_ORACLE_FOUNDATION.json). This corpus is separate
from C01's historical CLI fixtures. No vector is a real wallet secret.

```sh
cmake --preset cpu-release
cmake --build --preset cpu-release --parallel 4
ctest --preset cpu-release -R '^oracle_selftest$'
# Explicit regeneration; first verifies all results against the pinned library.
python3 tests/oracle/oracle_selftest.py --binary build/cpu-release/secp256k1_oracle \
  --report /tmp/keyhunt-oracle-regeneration.json --write-vectors
```

## CPU field arithmetic corrections

The C04 sanitizer log identifies signed overflow in Montgomery setup and the
low-word loop of delayed-shift inversion, plus shifts of negative coefficients.
Source inspection also finds missing final carry/reduction in specialized field
multiplication/squaring, noncanonical negation of zero, omitted exceptional point
addition branches, and zero-scalar table indexing. Independent differential
checks must establish these behaviors before fixes; CPU agreement alone is not
proof that arithmetic is correct. Existing CPU byte-alignment and application
leak findings remain separate unless explicitly covered by subsequent evidence.

The first CPU field run reproduced 33 failures in 12,552 cases, recorded in
[C06_FIELD_BEFORE.json](baselines/C06_FIELD_BEFORE.json) (first 20 diagnostics
retained). For example `2 * (2^255-1)` was returned unreduced. All three specialized
multiply/square variants now retain the 257th carry bit and subtract `p` when
needed. Their twice-folded intermediate is below `2*p`, so one subtraction
suffices, including full 256-bit operands. `ModNeg(0)` now remains zero.

Montgomery Newton inversion now uses unsigned arithmetic modulo `2^64`. The
DRS62 inversion's low words also use explicit unsigned wraparound and arithmetic
right shift; its bounded signed matrix coefficients use multiplication by two
instead of undefined left shifts of negatives. This preserves the intended
bit operations without compiler overflow flags or sanitizer suppressions.

`cpu_field_oracle` now passes 13,252 cases: canonical field add/subtract,
specialized multiply/square (including inputs at/above `p`), inverse, negation,
and scalar add/multiply modulo `n`. Binary tests cover distinct output, output
aliasing either operand, and in-place forms; self-multiplication tests alias all
operands. Nonzero inverse results use Python `pow(a,-1,p)`; the legacy zero-input
inverse sentinel is checked as zero, not treated as an actual inverse.

Release's complete nine-suite run passes, including all 38 CPU and five loader
cases. Debug and ASan/UBSan pass the oracle, field and 55-check verifier suites.
In particular, the previously failing C04 verifier now passes with
`ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1`. See
[field validation](baselines/C06_FIELD_VALIDATION.json). This does not clear the
application's unrelated alignment/leak findings and makes no performance claim.

C06 remains in progress; exceptional point and bounded search tests follow.
No GPU arithmetic or search has been implemented.
