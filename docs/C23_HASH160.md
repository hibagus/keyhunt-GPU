# C23 first family: Bitcoin P2PKH and HASH160

Status: implementation in progress. The user selected Bitcoin address and raw
HASH160 coverage for this pass. Ethereum, vanity, minikeys and other GPU mode
families remain pending under C23; this slice does not complete the whole row.

## Contracts and decisions

New exact `hash160` and `address` commands will use the bounded scalar planner,
CPU-verified candidates and native HIP/CUDA executors. `address` accepts Bitcoin
mainnet P2PKH Base58Check only, with checksum and canonical-encoding validation.
P2SH, witness, testnet and Ethereum inputs fail explicitly. Existing legacy `-m`
commands retain their CPU behavior. An address file and its equivalent raw-hash
file describe the same canonical job when their encoding selection agrees.

A target is 21 bytes: encoding tag 1 (compressed SEC1) or 2 (uncompressed SEC1),
followed by the full 20-byte HASH160. `--encoding compressed|uncompressed|both`
selects these relations; both is the default. Canonical sorted unique targets
and a new domain-separated digest bind encoding as well as hash bytes. Two
encodings may match at one scalar, and those remain distinct verified results.
No assumption about the number of hash preimages is used to size output buffers.

The device pipeline computes SHA-256 over the serialized public key, then
RIPEMD-160 over that digest. Its portable integer implementation follows
[FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final) and the
[RIPEMD-160 authors' specification](https://homes.esat.kuleuven.be/~bosselae/ripemd160.html).
Independent fixtures combine pinned libsecp256k1 public keys with Python/OpenSSL
hashes. The host retains the separately implemented CPU hash/curve verifier.
A completed GPU launch alone never credits durable coverage.

Mode 3 will identify HASH160 in manifests. Its targets include encoding tags;
its 50-byte algorithm binding has zero table/BSGS parameters. Existing schema-v7
columns and checkpoint records already hold scalar/target pairs, so no published
migration needs alteration. Unknown mode values must fail explicitly. Modern
workers advertise hash160-v1; the coordinator will reject hash jobs for workers
without that capability before reservation. Existing xpoint/BSGS clients remain
supported by the updated coordinator. New workers require the updated coordinator.

Candidate capacity is bounded by scalar count and enabled encodings, not target
count. Both encodings require room for at least two candidates so a one-scalar
replay can always complete. Overflow discards the entire attempt and replays
smaller scalar batches. Target identity, counters, guards and every candidate
are checked before any batch contributes coverage.

The [A21 terminal-exit correction](TERMINAL_EXIT_RECOVERY.md) is a prerequisite.
Hash jobs will use the same persistent device owners, local controls, fences,
exact remaining-range replay, bounded outbox and C22 file exchange as existing
modes. BSGS launch tuning from A22 is outside this feature slice.

## Acceptance gates

- Canonical address/hash loading, compression identity, bounded malformed input,
  independent hash vectors and candidate rejection on CPU/debug/sanitizer builds.
- Native HIP and CUDA hash/point parity, direct and stepped kernels, high-bit
  ranges, curve-order tails, both encodings, dense overflow/replay and no-match
  coverage. CPU builds explicitly refuse GPU execution.
- Durable complete/retry, process interruption, pause/resume, exact result/union
  audit and rejection of changed inputs or invalid receipts.
- Coordinator capability checks, authenticated supervised execution, persistent
  reuse and offline file reconciliation for the new mode on both GPU hosts.
- Appropriate old-mode regressions, documented commands and source/binary/raw
  evidence hashes. No new performance claim without separate measurements.

## Implementation evidence

The canonical input and CPU verification layer passes three release tests
(`hash160_search_contract`, `work_unit`, `xpoint_search_contract`) and both new
contract/planner tests under ASan/UBSan with leak detection. Public scalar-1
vectors cover compressed and uncompressed addresses. Malformed, overlong,
wrong-network, checksum-invalid and noncanonical input is rejected. Tests also
verify that two encoding matches at one scalar are valid, while repeated
scalar/target pairs and wrong execution identities are rejected.

At this stage the new mode is not exposed as a native execution command.

The short-message hash primitives pass 667 independent Python/OpenSSL vectors
on host C++ and native MI300X HIP, plus the host ASan/UBSan build. This includes
every supported message length, SHA padding boundaries, randomized bytes,
rejected lengths and a fixed scalar-1 HASH160 vector. OpenSSL 3 on this host
requires its legacy provider for the independent RIPEMD-160 test oracle; the
test explicitly loads that provider in a subprocess when hashlib lacks it.
CUDA primitive validation and search-kernel acceptance are still pending.

Standalone `hash160` / `address` execution is now wired to separate native
direct and stepped owners. The portable primitive corpus also passes on H200
CUDA. On MI300X, both kernels pass dense every-index tails, two-encoding replay,
ownership/ticket checks and 31 injected failure boundaries. Each kernel's CLI
corpus passes 47 independent small-range cases (including all eight devices),
with pinned libsecp256k1 points and independent OpenSSL hashes. CPU CLI checks
confirm an explicit unavailable-backend error. Maximum-batch and durable-mode
acceptance remain in progress.

Durable HASH160 mode now uses mode 3 with unchanged schema-v7 migrations and
checkpoint encoding. The scalar runner is shared with xpoint; HASH160 validates
unique scalar/target relations, while xpoint retains its unique-scalar rule.
CPU recovery and ASan/UBSan tests pass for interrupted commits, exact remaining
ranges, two encodings at one scalar, pause/resume, invalid receipts and audit
corruption. Existing xpoint/BSGS recovery regressions pass after this refactor.

Native HIP checkpoint CLI tests pass high ranges, curve-order address inputs,
no-match completion, changed-input rejection, process-kill recovery and finished
retries. The dedicated HASH160 pause test also passes repeated pauses, snapshot
inspection, graceful stops and resumption with changed visible-device layouts.
Both HIP search variants pass the maximum 1,048,576-scalar batch offset corpus.

Coordinator support now advertises `hash160-v1`. Old two-capability workers
remain accepted for xpoint/BSGS; requesting a HASH160 job without the third
capability fails with HTTP 426 before reservation or receipt replay. Unknown
wire modes fail explicitly. New unit tests pass canonical import, two-encoding
server verification, lost-response retry and acknowledged outbox cleanup; the
existing sync/worker/dispatch/offline tests also pass.

On MI300X, authenticated HTTPS supervision and disconnected file-only execution
both complete two HASH160 grants with one executor setup. Both encodings survive
local persistence and later authenticated server reconciliation. Native H200
checkpoint CLI and changed-visibility pause/restart tests also pass. CUDA direct
CLI validation is being repeated after a test/build overlap replaced its binary;
the prior run reported a process-launch permission error, not a result mismatch.
